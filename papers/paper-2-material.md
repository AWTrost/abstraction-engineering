# Paper 2 material

Paper 2 is classes in action: a class at work, and how it learns from its own runs. This note gathers what the v0 build of release-review showed about that, from the session that ported the class to an npm package, installed it for one team and measured it. It adds to the "For paper 2" list at the end of paper 1 and repeats none of it. Items marked (Nov 10) come from the next day, when the class was published to an internal npm registry and installed as a pinned dev dependency in two repos. Items marked (Nov 12) come from a review of paper 1 by a model with no part in the build. They are ideas, not observations, so they all sit under "Where the model sits". It is one class, one team and two days of runs, and still a proof of concept. So every item outside "Where the model sits" is an observation, not a result, and every item inside it is an idea.

## Memory and instance state

- **Two sessions, one work item, one Now block.** Two sessions worked on the same work note on the same day. One rewrote the Now block after the other had updated it, so it still asked for a review of a pull request that had already merged. The checkpoint rule (verify every claim against live state before writing) caught it. Instance state that several sessions write needs either a merge rule or a check on read, not just a timestamp.
- **A class's output was overwritten as evidence.** Reports are named by release id only. A later run of the same release, from another session, overwrote the report the paper's Release B score came from. The figures survived only because they had been copied into the comparison note. A report is instance state of a finished run, and a class that keys it only by its input loses history. A run id or an append-only report folder would keep it.
- **The class did not record its own token use.** The report keeps `cost_usd` and nothing else, though the model call returns full usage. The comparison in paper 1 had token counts for the hand-run session and only dollars for the class. A class that is meant to be measured across runs has to record what is measured, from the first run.

## Failure that looks like success

- **The never-throw contract hid a setup error.** The fuzzy function turns any failure into the verdict `unclear`, so a bad binding never crashes a run. But stripping the user's setup for cost also strips variables set in the agent's settings file, which is where some people configure their model provider. For them every call fails, every verdict comes back `unclear`, and the report looks complete. Fail-soft per item is right; fail-soft for a cause that hits every item is a silent outage. The fix shipped was a hint in the failure reason. A better one is a run-level check: if every verdict failed the same way, stop.
- **Isolation and identity pull against each other.** The class runs "with the provider and auth of whoever runs it". Stripping the runner's agent configuration keeps house context out of the judgement. It also cut the cost of one three-word call about 135 times, from $0.149 to $0.0011 (paper 1). That is the overhead taken off each call, not the ratio for a real call, which also carries a ticket and its changes. But that configuration is also where part of the runner's identity lives. A class has to say which parts of the runner's environment it inherits.
- **An optional input is a silent failure.** (Nov 10) If a judgement depends on an input the contract does not require, a setup that leaves it out gets a report that looks complete and is wrong. It is the never-throw item above, at the level of the contract. The next section has the case that showed it.

## Promotion and gates

- **Each reviewer caught a different kind of error.** On one paper edit, percy (a cold reader with no context) found four must-fix problems, including a call count the drafting agent had estimated and written as fact ("about 6"; it was 8). Cody (the code reviewer) then found a per-call figure that counted only cache reads. The tests and the marker check passed throughout. Estimates turn into facts as text is drafted, and a reader without the author's context is what catches them.
- **A plan cold-read before building.** Percy read the implementation plan before any code and found four must-fix problems: a comparison that could not run, a "no behaviour change" claim that the design contradicted, a schema the planned validator could not express, and a command that could not find its data once installed. All four would have surfaced later as bugs or rework.
- **The human decision changed the build, and a cheap experiment settled it.** I chose to keep the package in the existing repo. That made "npm installs a subfolder" a premise, and a two-minute test in a scratch repo showed it false. The release mechanism (a tag on a subtree split) came from that test, not from reading documentation.
- **A lesson from one run became a class version the same day.** (Nov 10) The first run in a second repo exited cleanly, and its report looked complete: 28 matches and 1 unclear, for $0.69. Reading it, I saw that many verdicts said no diff had been shown. The contract had no diff input, so the model judged each ticket from commit titles and descriptions. A binding could have added a diff, and the class would have passed it on with no cap and no mention in the prompt. The lesson became a rule: every input a judgement depends on has a required binding. The rule became release 0.3.0: a required capability that returns each change's diff, a 20,000-character cap, and three conformance cases where the commit text and the diff disagree. It scored 17 of 19 on the conformance set with no hard misses, for $0.18. It was published, re-pinned in the repo and re-run the same day: 28 matches, 0 unclear, 1 partial. Every check had passed on the first run. A person reading the report found the lesson, which is promotion through a gate.
- **Letting the function see more changed a test's label.** (Nov 10) With diffs, a case whose change only added a TODO stopped being unclear and became unrelated, so its expected answer was changed. The code reviewer flagged the relabel as a judgement call for me. A contract change can mean relabelling the conformance set, and the relabel needs the same gate as any other promotion.
- **More reviewers, more kinds of error.** (Nov 10) An automated merge-request reviewer found three bugs in one repo's bindings: the range start could pick a tag cut after the end tag, a merge commit was counted twice, and an option went unvalidated. The fixes came with four tests that fail on the old code. Separately, the code reviewer caught a pull request that claimed more than its check proved: a login probe showed that the job could authenticate, not that it could publish. Only a real publish settled that.

## Bindings

- **The binding shapes the verdict.** (Nov 10) The diff binding left out the lockfile to save space. One ticket was a dependency upgrade, and with the lockfile hidden its verdict came back partial, which was wrong. The binding now adds a line saying the lockfile changed, and the re-run gave 29 of 29 verdicts match. What a binding leaves out is part of the judgement, not just plumbing. "Match" here is the verdict the model gave; nobody has scored these verdicts against a ground truth.
- **A binding replaced in another language.** (Nov 10) The repo's bindings were rewritten from Python to Node to fit its toolchain. On live data the Node output equalled the Python output for three release ranges and 40 diffs, and the full run then gave the 29 of 29 above. Equal output on live data is a substitution check for a binding, as the conformance set is for a model.
- **Bindings copied between repos.** (Nov 10) The second repo's bindings were ported from the first, and the reviewer's fixes had to be ported by hand after them. Two setups now hold near-copies of the same code. That suggests the shared part belongs in the class or in a shared binding library, but it is two copies, not three, so by the rule of three it waits.

## Self-maintenance

- **A closed set of keywords.** The class checks its contract with a small validator that supports only the JSON Schema keywords the contract uses. A test walks the contract and fails on any other keyword, so a keyword the validator would silently skip cannot enter the contract unnoticed. This is a pattern for any partial implementation of a standard: keep the set closed, and test that it is.
- **A contract change is a version bump, and the pin makes it deliberate.** Tightening the accepted shapes made the class 0.2.0, and the real setup pinned to 0.1.0 was refused until re-pinned. The tightening was checked against the real binding's output before it landed, and the re-pinned setup passed on the first run.
- **Release identity is content, not history.** A squash merge forced a rebase after the release tag was pushed. The tag stayed valid because the package's tree was identical before and after. Pinning by tag works because the lockfile records a commit, and the check that matters is the tree.
- **A squash merge dropped the imported history.** (Nov 10) When the class moved into its internal repo, the merge client squashed the import, though the project's default keeps commits. The history now survives only on a tag. For a class whose history is evidence, the merge setting is part of its memory.

## Sharing and adoption

- **A try that touches nothing.** The class was installed for one team's repo as a trial without editing any tracked file: a global install, and the skill linked into a folder the repo already ignores. The team path is a committed devDependency. A trial that needs no change to the team's repo lowers the cost of a first run.
- **A fresh agent needed nothing but the contract.** Told only to "use the release-review agent-class", an agent found the skill, passed the two declared inputs and stopped at sign-off. Through the agent, though, the run cost about three times running the class from a shell, mostly the agent's own setup.
- **The public registry is part of the threat model.** The package name was unclaimed on the public npm registry, so a plain `npx release-review` with the package missing would fetch whatever someone later published under that name. The skill uses `npx --no`, and the package is marked private.
- **Installed as a pinned dev dependency in two repos.** (Nov 10) A tag-triggered job publishes the class to the internal registry, one package per class. The home repo's copy drops the `private` flag and pins publishing to that registry; the public showcase copy keeps `private`, so it cannot be published anywhere. Two repos install it at an exact version: the repo whose setup paper 1 used, and a second repo of the same team. Each holds its own bindings, setup file and skill, and check-setup passes in both. The paper 1 repo's run on its next release took 43 seconds and cost $0.39, with 8 of 8 verdicts match. By my own account, the class ran through each runner's own provider and auth with no trouble, so the provider trap above did not bite in these runs. It is still a proof of concept: no teammate has run it, and both merge requests are waiting for review.
- **One package per class.** (Nov 10) A bundle of every class would couple their versions. Each setup refuses any version but the one it pins, so a fix in one class would force an upgrade of every class on every team.
- **The skill text is partly setup.** (Nov 10) The packaged skill lacked details each repo needs, such as its release-id format and how to preview against its main branch. Agent-facing text splits along the class/setup line too, and each repo's copy of the skill carries the setup half.
- **The install meets the repo's own tooling.** (Nov 10) In one repo, a postinstall script links skills into the agent folders, and its clean mode would delete the link the class's installer makes. The skills folder is ignored by git, so each developer must run the installer. On the wrong Node version, npm rewrote 272 lockfile lines; on the repo's pinned version, the change was one entry.
- **The internal scope is public too.** (Nov 10) The scope the class is published under is also a scope on the public registry, owned by another project. A repo without the line in its npm config that maps the scope to the internal registry would make its first install from the public one. Today the name is missing there, so that failure is loud. After the first install, the lockfile pins the internal tarball.

## Where the model sits

These are ideas, not observations from a run. The unmarked ones come from a conversation after the first run of the class on the work machine, with the same setup as paper 1. The ones marked (Nov 12) come from the review of paper 1. Each is marked with what would test it.

- **The chat session is the IDE, the class is the code.** There are two kinds of AI work. One is the chat session with a person in the loop, which everyone knows. The other is the tools and automation that run underneath it. The second is the code we build, and the chat session is the new IDE we build it in. Paper 1 holds both halves without naming the split: "an agent's place moves to setup time", and the program drives while the model fills functions. The split explains the agent route costing about three times a shell run: running the build output through the IDE loads the IDE's context first. The gate is a third part. A person signing off a release is judging in the loop, not editing. So the split may be three parts: the IDE (building), the program (running) and the gate (deciding). A sharper form of paper 1's claim: what a session leaves behind is a program other people can run, not a transcript. Test: as teammates run the class, record which runs went through an agent and which from a shell, and the cost of each.
- **Fewer tokens for the same output.** When the model runs only for the fuzzy step, nobody pays tokens for the exact work or for the turns back and forth. On release B the hand-run session made 19 calls and read 1.34 million tokens to reach its hand-off list, about 71,000 a call, mostly re-reading the conversation. The class made 8 small calls for $0.14. Two qualifications. While tokens are cheap, people spend them to save their own time, so price is the weaker half of the case; the same steps every run, small judgements a test can check, and one command for a teammate hold whatever tokens cost. And building the class cost tokens too, so the fair comparison spreads the build cost over every run by every teammate. Test: teammates' runs, with tokens recorded per run, on releases of different sizes.
- **A small model for the fuzzy functions.** A one-shot call with a fixed type, no tools and a short context is where a small model does well. On the conformance set a small model already scored 16 of 16 for about a cent, while the live runs used a mid-size model. A local model needs no class change: a fuzzy function can be bound to a command, and a script that calls a local model is one more binding. The conformance set decides whether it may substitute, which is the Liskov check. A local model from another vendor would also answer paper 1's thesis question 2, and repeated runs give the flip rate. Test: score a small local model on the conformance set, several times.
- **Commands in place of servers for repeated jobs.** A tool server exists so an agent can call tools across a long session. Without an agent loop, most of that reason goes. A class calls a command, reads JSON and the process exits, so it runs the same from cron or CI as from a shell, and a scheduled job needs no chat session and no server running. A server still earns its place for setup too costly to repeat on every call (an auth handshake, a large index, a warm local model), for events pushed to it (a webhook needs a listener), and for state shared between runs (a cache, a rate limit, a memory store). A rule to test: a server for what must listen or stay warm, a command for everything else. Unattended runs raise the stakes on two items above. A silent all-`unclear` run from cron is seen by nobody, so the run-level check becomes required. Scheduled runs of one release overwrite each other's reports, so the run id becomes required. The gate stays human: a scheduled run writes a draft that still needs sign-off. Test: one scheduled run of the class, with both fixes in.
- **A doctor for missing bindings.** (Nov 10) After install, a command lists the capabilities a repo has not bound and prints a prompt an agent can use to draft them. That gives an agent a defined place at setup time, which paper 1 names but does not build. Test: bind a new repo through the doctor alone, and count the hand edits after it.
- **Review agent-facing text on upgrade.** (Nov 10) A class package ships prompts and skill text that an agent acts on, so an upgrade can change what agents do without any code change. The review would diff that text between the pinned and new versions, and check that the package came from the expected registry. Test: one upgrade run through the review, with a planted prompt change it should catch.
- **A session discovers the process, and a class is what it compiles into.** (Nov 12) This sharpens the first item in this section. The first time a piece of work is done, nobody knows the process, and a long session makes it up as it goes. Afterwards the exact steps are known and can be code. The rule of three then says when to compile: the third time the same session shape comes back. Test: for the next class, record the sessions it was compiled from, and which of its steps nobody could have named before them.
- **Pin the model and the tool, not only the class.** (Nov 12) A setup names a model, and the example setup uses a short alias. If a vendor points the alias at a newer model, every verdict can change with no new class version and no re-pin. The coding agent's command-line tool is unpinned too. Test: a setup that names a dated model id, a report that records the exact model and tool version, and one conformance run before and after a model change to see how many cases move.
- **Independent calls can be run cheaper.** (Nov 12) Each call to the fuzzy function depends on no other. So the calls could run side by side, go to a batch interface, or go to a small model first with only the non-`matches` answers sent to a larger one. A cache keyed on a hash of the exact inputs would also make a re-run pay only for items that changed, which fits a release reviewed more than once as it fills. The key has to include the prompt, the schema and the exact model, or a changed prompt would be answered from old verdicts. The class makes its calls one after another today. Test: one release run each way, with the time, the cost and the verdicts compared.
- **Show agreement, not only the first answer.** (Nov 12) A cache makes a re-run repeat itself, and so hides how often a verdict would flip. Test: sample each verdict several times on one release, print the agreement beside each verdict, and see whether the low-agreement ones are the ones a person disputes.
- **Wrong pairs on purpose.** (Nov 12) Live runs so far gave 29 of 29 and 8 of 8 `matches`, so they do not show that the function can say anything else. Pairing each real ticket with another ticket's changes gives cases whose right answer is `unrelated`, with no labelling. Test: shuffle the pairs of one real release and count the `matches` answers, each of which is a hard miss.
- **A known-answer release for each setup.** (Nov 12) The class's tests check the shape of a capability's output, not its meaning, and a binding with the right shape gave the wrong release window. A team could keep one past release with a known list of changes and tickets, and run its real bindings against it after every binding change. It belongs outside every shared repo, as the team's own conformance cases do. Test: build one, then put back the binding defects found so far and count how many it catches.
- **A larger conformance set.** (Nov 12) No hard miss in the 10 `partial` and `unrelated` cases still allows a hard-miss rate of up to about 26% (paper 1 has the working). By the same working, ruling out a rate above 5% needs about 59 such cases with no hard miss, and above 1% about 299. Test: grow the set from real past releases, held out from whoever writes the prompt, and report the bound with each score.
